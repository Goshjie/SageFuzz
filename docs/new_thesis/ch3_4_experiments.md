# 3.4 实验与分析

本节通过五类代表性有状态 P4 程序上的实验，从测试用例结构完整性、确定性一致性校验、生成开销和缺陷触发能力四个维度评估 P4-BISG 方法的有效性。

## 3.4.1 实验设置

### （1）研究问题

本章实验旨在回答以下四个研究问题：

- **RQ1（结构完整性）：** P4-BISG 生成的测试用例是否具备完整的多维结构？
- **RQ2（一致性校验）：** 生成的测试用例是否通过了数据面、控制面和执行序列三个层面的确定性一致性校验？
- **RQ3（生成效率与需求覆盖）：** 系统的生成耗时和规范需求覆盖率如何？
- **RQ4（缺陷触发能力）：** 生成的测试种子在真实 BMv2 环境中是否能够区分正确实现与缺陷实现？

### （2）实验对象

实验选取五类具有代表性的有状态 P4 程序，覆盖了安全策略、网络监测、流量工程等典型应用领域。表 3-7 列出了各程序的基本信息。

**表 3-7 实验程序概况**

| 程序 | 核心有状态机制 | 测试场景类型 | 控制面依赖 |
|------|--------------|------------|:--------:|
| Stateful Firewall | 双布隆过滤器连接跟踪 | 策略验证（正/反例） | 有 |
| Link Monitor | 逐跳计数器与探针追加 | 遥测监控 | 有 |
| Heavy Hitter Detector | 计数最小草图（Count-Min Sketch） | 阈值行为验证 | 有 |
| Fast Reroute | 链路状态寄存器与备份下一跳 | 跨阶段路径切换 | 有 |
| Congestion-Aware Load Balancing | 队列深度监测与拥塞反馈 | 负载感知重分流 | 有 |

五类程序涵盖了 3.2 节所述的三个技术难点：Stateful Firewall 侧重结构性映射差距，Link Monitor 侧重约束定位，Fast Reroute 侧重各维度间一致性。Heavy Hitter Detector 和 Congestion-Aware Load Balancing 进一步扩展了对持续流量驱动和拥塞感知场景的覆盖。

## 3.4.2 RQ1：测试用例结构完整性

表 3-8 汇总了五类程序上生成的测试用例结构统计信息。

**表 3-8 测试用例联合生成结构统计**

| 程序 | 场景数 | 数据包数 | 规则实体数 | 控制面操作数 | 执行序列操作数 | 包序列状态 |
|------|:------:|:-------:|:---------:|:----------:|:------------:|:--------:|
| Stateful Firewall | 2 | 3 | 3 | 3 | 6 | PASS |
| Link Monitor | 1 | 21 | 1 | 1 | 22 | PASS |
| Heavy Hitter Detector | 2 | 30 | 3 | 3 | 33 | PASS |
| Fast Reroute | 3 | 20 | 9 | 11 | 31 | PASS |
| Congestion-Aware LB | 2 | 15 | 3 | 3 | 18 | PASS |
| **合计** | **10** | **89** | **19** | **21** | **110** | — |

五类程序共产生 10 个测试场景、89 个数据包、19 条规则实体、21 个控制面操作和 110 个统一执行操作。不同程序的测试用例规模差异较大，与各自的测试语义复杂度相关：

- Stateful Firewall 的测试用例最为紧凑，仅用 2 个场景和 3 个报文就表达了内部发起允许、外部发起拒绝两类方向性策略行为。
- Link Monitor 以 21 个数据包表达持续流量驱动计数累积与探针观测的监控链，其中 15 个为业务流量、1 个为探针。
- Heavy Hitter Detector 需要 30 个数据包驱动 Count-Min Sketch 的计数累积，以触发阈值跨越前后的行为差异。
- Fast Reroute 是规模最大的测试用例，通过 3 个场景、20 个数据包和 9 条流表规则，配合 11 个控制面/外部操作表达从正常转发到链路失效到控制器收敛的完整路径切换过程。
- Congestion-Aware Load Balancing 在 2 个场景中组织了正常分流与拥塞后重分流的行为。

所有测试用例的包序列状态均为 PASS，即满足场景契约中的角色绑定、协议栈层级和字段位宽约束。

**结论：** P4-BISG 能够针对不同类型的有状态 P4 程序生成结构完整的多维测试用例，覆盖数据面报文、控制面规则、外部操作和统一执行时间线。

## 3.4.3 RQ2：确定性一致性校验

为验证测试用例的内部一致性，本文从控制面结构、执行序列和观测规约三个层面对每个场景执行离线确定性校验。表 3-9 展示了逐场景的校验结果。

**表 3-9 确定性一致性校验逐项结果**

| 程序 | 场景 | $V_{\text{table}}$ | $V_{\text{action}}$ | $V_{\text{match}}$ | $V_{\text{param}}$ | $V_{\text{cover}}$ | $V_{\text{cp-order}}$ | $V_{\text{exec}}$ | $V_{\text{oracle}}$ | 总体 |
|------|------|:---:|:---:|:---:|:---:|:---:|:---:|:---:|:---:|:---:|
| Stateful Firewall | positive_internal | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| Stateful Firewall | negative_external | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| Link Monitor | link_utilization | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| Heavy Hitter | threshold_triggered | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| Heavy Hitter | new_flow_unaffected | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| Fast Reroute | baseline_forwarding | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| Fast Reroute | post_failure_reroute | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| Fast Reroute | post_reconverge | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| Cong-Aware LB | baseline_distribution | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| Cong-Aware LB | congestion_reroute | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |

其中八项校验指标含义如下：

- $V_{\text{table}}$：规则引用的流表在目标程序中真实存在。
- $V_{\text{action}}$：规则指定的动作被对应流表允许。
- $V_{\text{match}}$：规则的匹配键字段完整。
- $V_{\text{param}}$：动作运行时参数齐全且位宽合法。
- $V_{\text{cover}}$：规则集合覆盖了报文序列中的目的地址。
- $V_{\text{cp-order}}$：控制面操作序列的引用与实体一致。
- $V_{\text{exec}}$：执行时间线中数据面和控制面引用完整且序号递增。
- $V_{\text{oracle}}$：预言机预测的结构与报文序列一一对齐。

10 个场景在全部八项校验中均通过。需要说明的是，全部通过并不意味着校验流于形式：八项校验中前四项（$V_{\text{table}}$、$V_{\text{action}}$、$V_{\text{match}}$、$V_{\text{param}}$）的正确性依赖于生成模块在构造控制面规则时通过 ProgramContext 的 TABLE\_SIGNATURE 工具查询获取真实的流表签名、动作列表和参数类型。换言之，流表名称、动作名称和匹配键字段并非由语言模型自由生成，而是从编译产物的索引中查询得到后填入规则模板。这一设计从源头上消除了模型"编造"不存在的流表名或动作名的可能性。类似地，$V_{\text{cover}}$ 和 $V_{\text{cp-order}}$ 依赖于规则生成阶段对拓扑信息和场景结构的工具查询结果，$V_{\text{exec}}$ 和 $V_{\text{oracle}}$ 则是在输出封装阶段通过结构化对象间的引用关系自动校验得出。因此，全部通过反映的是"基于工具查询的受约束生成 + 阶段间确定性校验"这一架构设计的有效性，而非偶然结果。

**结论：** 确定性校验机制有效保证了测试用例在控制面结构、执行序列和观测规约三个层面的内部一致性。校验能够全部通过的关键在于系统的约束信息来源于对编译产物的工具查询而非模型的开放式生成。

## 3.4.4 RQ3：生成效率与需求覆盖

表 3-10 统计了各程序的生成耗时、包序列轮次和规范需求覆盖率。

**表 3-10 生成效率与需求覆盖统计**

| 程序 | 场景数 | 正向 | 反向 | 包序列轮次 | 生成耗时/s | 需求覆盖率 |
|------|:------:|:----:|:----:|:---------:|:---------:|:---------:|
| Stateful Firewall | 2 | 1 | 1 | 1 | 87.41 | 1.00 |
| Link Monitor | 1 | 1 | 0 | 1 | 117.90 | 1.00 |
| Heavy Hitter Detector | 2 | 2 | 0 | 1 | 416.49 | 0.50 |
| Fast Reroute | 3 | 3 | 0 | 2 | 704.16 | 1.00 |
| Cong-Aware LB | 2 | 2 | 0 | 1 | 144.89 | 1.00 |

生成耗时的分析如下。五个程序的测试种子均能在秒级到数百秒级内自动生成（平均耗时 294.17 s）。Stateful Firewall 和 Link Monitor 的生成耗时较短（87~118 秒），因为场景结构紧凑且约束数量有限。Congestion-Aware Load Balancing 耗时约 145 秒，处于中等水平。Heavy Hitter Detector 耗时约 417 秒，主要原因是 30 个数据包的序列构造需要反复查询 Count-Min Sketch 相关的有状态对象约束。Fast Reroute 的耗时最长（约 704 秒），因为涉及三个场景、9 条流表规则和多个外部操作的编排，且需要 2 个包序列轮次（第一轮部分校验未通过，触发修复后在第二轮通过）。生成开销主要受测试意图复杂度和程序行为结构影响：对于策略/计数型程序，系统能快速生成规模较小但语义明确的用例；对于涉及链路故障恢复、路径迁移的复杂程序，生成时间和控制平面开销有所增加，但仍在可接受范围内。

需求覆盖率方面，四类程序达到 1.00，即规范中要求的所有维度（正反例、外部操作、观测需求）均已在生成结果中体现。Heavy Hitter Detector 的覆盖率为 0.50，原因是规范要求同时生成阈值触发前的反例场景（大量包发送后仍不触发），但当前生成未完整实现该反例的观测标准。

**结论：** P4-BISG 能够在可接受的时间范围内（平均约 294 秒）完成测试用例生成，需求覆盖率普遍达到 100%。总体而言，该方法省去了人工逐包设计流量和逐条配置规则的工作。

## 3.4.5 RQ4：缺陷触发能力

状态覆盖仅证明了理论语义的完备性。为验证生成的测试种子是否具有实际测试价值，本实验在每个目标程序中注入独立的缺陷（遵循仅修改测试意图相关关键逻辑的原则），并通过脚本将生成的 JSON 格式 Testcase 恢复为真实网络协议栈报文和外部动作，在远程 BMv2 Mininet 环境中直接回放。表 3-11a 汇总了各程序的直接回放验证状态。

**表 3-11a 各实验程序直接回放验证状态**

| 程序 | 可直接回放 | 与 oracle 一致 | 区分正确/缺陷实现 |
|------|:---:|:---:|:---:|
| Stateful Firewall | ✓ | ✓ | ✓ |
| Heavy Hitter Detector | ✓ | ✓ | △ |
| Fast Reroute | ✓ | ✓ | ✓ |
| Link Monitor | ✓ | △ | ✓ |
| Congestion-Aware LB | ✓ | △ | △ |

表 3-11b 进一步展示了每个程序的缺陷注入细节与回放观测结果。

**表 3-11b 最终 Testcase 直接回放实验结果**

| 程序 | 注入缺陷说明 | 回放实际观测结果 | 结论 |
|------|------------|----------------|------|
| Stateful Firewall | 错误阻断已建立连接的回包 | 正确版：正反例行为正常；缺陷版：正例 SYN-ACK 在入口被异常阻断 | 可直接回放，稳定区分正确与缺陷实现 |
| Heavy Hitter Detector | 阈值设置过小导致提前阻断 | 回放 15 个包后，正确版按预期捕获，缺陷版捕获数量少于预期（10 个） | 可直接回放，并与预言机 (Oracle) 一致 |
| Fast Reroute | 禁用本地备份路径切换 | 触发链路失效后，正确版捕获 10 个包，缺陷版捕获 0 个包 | 可直接回放，稳定区分正确与缺陷实现 |
| Link Monitor | probe 返回计数字段写零 | 正确版返回非零 byte_cnt，缺陷版为零；但用例中 probe 路径约束不足 | 可直接回放，能揭示差异，但观测语义需完善 |
| Cong-Aware LB | 提高反馈触发阈值 | 报文可成功送达；但拥塞注入动作描述较抽象，未稳定观测到重路由 | 可直接回放，但环境操作动作语义需完善 |

以下对实验结果进行分析。

**有效区分缺陷。** 本章方法生成的测试种子能在多个程序中有效区分正确实现与缺陷实现。在 Stateful Firewall 中，注入的缺陷将布隆过滤器匹配后的回程放行条件取反，导致已记录的合法回程流量被错误丢弃。使用生成的正向场景种子，正确版本完成 TCP 连接，缺陷版本在入口即丢弃回程包，行为差异清晰。在 Fast Reroute 中，注入的缺陷禁用了本地备份路径切换逻辑，触发链路失效后正确版捕获 10 个包，缺陷版捕获 0 个包，准确命中了逻辑漏洞。在 Heavy Hitter Detector 中，将检测阈值设置过小导致提前阻断，回放 15 个包后正确版按预期捕获，缺陷版捕获数量仅为 10 个，差异与预言机预测一致。

**具备直接可执行性。** 系统输出的 Testcase 已具备在真实环境中的执行能力。前三个程序（Stateful Firewall、Heavy Hitter Detector、Fast Reroute）已实现了环境动作、报文序列与 Oracle 一体化的完整闭环验证。

**观测语义的局限性。** Link Monitor 与 Congestion-Aware Load Balancing 虽已证实可执行，但实验也暴露出系统在表达高度复杂的观测路径语义和抽象拥塞注入动作时仍有优化空间。Link Monitor 的用例中 probe 路径约束不足，Congestion-Aware Load Balancing 的拥塞注入动作描述较抽象，未能稳定观测到重路由行为。这表明，本章方法生成的测试种子已可在实际环境中执行，但在部分复杂场景下的观测语义表达仍有提升空间。

**结论：** P4-BISG 生成的测试种子在五类有状态 P4 程序上均可直接回放，其中三类程序稳定区分了正确实现与缺陷实现，两类程序虽能揭示差异但观测语义需进一步完善。这表明系统生成的多维测试用例在结构上一致，在实际执行中也具备缺陷检测能力。

## 3.4.6 结果讨论

综合上述四个研究问题的结果，可以得到以下讨论。

**结构化与可执行性。** 与传统方法输出单包或验证结论不同，P4-BISG 生成的是包含报文序列、控制面规则、外部操作、统一执行时间线和观测预言机的完整测试用例。五类程序共产生 89 个数据包、19 条规则实体和 110 个统一执行操作，测试种子可被直接回放，校验结果可被量化追踪。

**确定性校验的作用。** 10 个场景全部通过八项确定性校验，说明多阶段生成与校验回退机制能够将模型输出的不确定性约束在可控范围内，系统的可靠性不完全依赖于生成模型的准确度。

**工程实用性。** 五类程序的缺陷注入实验表明，生成的测试种子可以在正确实现上正常执行，并在缺陷实现上暴露行为偏差。其中 Stateful Firewall 和 Fast Reroute 实现了稳定的正确/缺陷区分，Heavy Hitter Detector 的量化差异数据与预言机预测一致。

## 3.4.7 局限性

尽管实验结果总体积极，本章方法仍存在以下局限性。

**程序覆盖范围有限。** 当前实验仅涵盖五类有状态 P4 程序。对于更复杂的生产级程序（如数据中心交换芯片固件），方法的扩展性尚需进一步验证。

**观测语义的完善程度不一。** Link Monitor 和 Congestion-Aware Load Balancing 的测试用例在结构上可直接回放，但在探针路径语义和拥塞注入动作语义上仍存在抽象性偏高的问题，说明观测规约和外部操作的参数化表达仍有提升空间。

**生成过程的非确定性。** 由于依赖大语言模型进行生成，不同运行之间的输出可能存在差异。虽然确定性校验机制可以过滤不合格输出，但无法完全消除生成过程本身的波动性。本文实验选取的是经过校验的成功运行结果。
