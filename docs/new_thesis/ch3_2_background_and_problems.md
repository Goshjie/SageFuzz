# 3.2 研究背景与研究问题

为了直观说明从 P4LTL 时序规范到可执行测试种子过程中面临的具体困难，本节通过三个典型的有状态 P4 程序场景展开分析。每个场景首先给出待验证的 P4LTL 时序性质，然后说明从该性质到可执行测试工件之间的差距，并侧重体现一类核心挑战。

## 3.2.1 场景一：有状态防火墙——时序规范到工件的结构性映射鸿沟

有状态防火墙（Stateful Firewall）通过双布隆过滤器实现基于连接状态的回程流量放行机制。当系统检测到由内部网络发起的 TCP SYN 数据包时，提取连接特征写入过滤器；对后续从外部进入的回程包，仅当特征在两个过滤器中均命中时才放行，否则丢弃。

针对该程序的 P4LTL 时序规范可表述为：

```
//#LTLProperty: [](AP(meta.direction == 0 && valid(hdr.tcp)
    && hdr.tcp.syn == 1 && !drop)
    ==> X(AP(meta.direction == 1 && !drop)))
//#LTLProperty: [](AP(meta.direction == 1 && bloom_filter_1[hash1] != 1)
    ==> AP(drop))
//#LTLFairness: [](AP(valid(hdr.ipv4) && valid(hdr.tcp)))
```

第一条性质描述了正向行为：当内部方向（`direction == 0`）的 TCP SYN 包未被丢弃时，下一个从外部方向到达的包应被放行。第二条性质描述了反向约束：当外部方向的包未命中布隆过滤器时应被丢弃。公平性条件限定了关注的包类型。

这些 P4LTL 性质在语义上精确完备，但距离可执行测试仍有显著距离。

首先，时序规范中**隐含了至少两个测试场景**——正向场景（内部发起、外部回包放行）与反向场景（外部主动发起被丢弃），但 P4LTL 公式的结构中并不存在"场景"的显式划分。其次，时序算子 `X`（next）隐含了**报文间的因果时序依赖**：SYN 必须先于回程包到达交换机，否则布隆过滤器中不会有匹配记录。但 `X` 只声明了"下一个时间步"的约束，不指定具体的协议类型和字段值。再次，原子命题中的 `meta.direction` 是**逻辑角色的抽象引用**，需要绑定到拓扑中的真实主机，并根据接入位置判定内外属性。最后，`drop` 和 `!drop` 谓词描述了**预期行为判定**，但并未指定在哪个观测点、以何种方式收集判定证据。

现有方法在此处的局限性体现得尤为明显。以 P4Testgen 为代表的路径求解方法可以给出命中某个表项的单包输入，但不输出"先建流、再回包"的时序步骤，也不负责给出角色绑定与观测标准。以 Chimera 为代表的模糊测试方法需要已有种子作为起点，但从零构造满足时序性质语义的初始种子正是本文要解决的问题。以 P4TV 为代表的时序验证方法可以判定 P4LTL 性质是否成立，但输出的是验证结论而非可回放的报文序列与控制面操作。

该场景集中暴露了**挑战一**的核心矛盾：P4LTL 时序规范描述的是"性质应成立"，而可执行测试工件要求的是"如何操作使性质可被验证"，两者之间存在结构性语义鸿沟。时序算子蕴含的场景划分、因果依赖、角色绑定和观测标准，需要一个系统化的规约过程将其显式化。

## 3.2.2 场景二：链路监测——程序约束异构下的规范落地困难

链路监测程序（Link Monitor）实现探针式的链路质量监测。普通 IPv4 流量正常转发；探针包在每跳追加交换机 ID、端口号、字节计数与时间戳，沿预置探针转发表转发，最终可还原路径上逐跳链路负载与时延变化。

针对该程序的 P4LTL 时序规范可表述为：

```
//#LTLProperty: [](AP(valid(hdr.probe) && valid(hdr.probe_data[0])
    && old(byte_cnt_reg[meta.port_id]) > 0)
    ==> AP(hdr.probe_data[0].byte_cnt > 0 && !drop))
//#LTLFairness: [](<>(AP(valid(hdr.ipv4) && !valid(hdr.probe))))
```

该性质声明：若探针包到达时对应端口的字节计数寄存器值大于零，则探针携带的 `byte_cnt` 字段应非零且包不被丢弃。公平性条件保证 IPv4 业务流量会持续到达以驱动计数累积。

该场景的核心困难在于：**正确生成满足 P4LTL 规范的测试工件所需的约束分散在多个异构数据源中**。具体而言：

- 规范中的 `hdr.probe` 和 `hdr.probe_data[0]` 使用程序自定义的探针头部而非标准协议头。其字段名称、位宽和嵌套关系定义在编译产物（BMv2 JSON）中，如果生成器不查询编译产物而凭借通用协议知识构造 probe 包，几乎必然产生字段名错误或位宽越界。
- 规范中隐含的探针转发路径由专用的 `probe_fwd` 表控制，该表的匹配键与动作签名记录在编译产物的表签名集合中。
- 规范引用的 `byte_cnt_reg` 寄存器的语义和索引方式定义在 BMv2 JSON 的有状态对象列表中。
- 公平性条件要求 IPv4 流量持续到达以驱动计数，发送端主机的选择依赖拓扑信息。
- 控制流图（CFG DOT）中的表跳转关系决定了报文经过解析器后进入正常转发还是探针处理路径。

上述五类约束分别来自编译 JSON、控制流 DOT、拓扑 JSON、有状态对象定义和可选 P4 源码。将它们全部拼接进生成模型的输入窗口既不现实也不高效。而如果不提供这些约束，模型极易产出不存在的探针字段名、错误的寄存器索引或不合理的发送端选择。

该场景集中暴露了**挑战二**的核心矛盾：P4LTL 原子命题引用的字段、寄存器和转发行为需要与多个异构数据源中的真实定义对齐，生成过程必须有系统化的手段从这些数据源按需获取精确约束。

## 3.2.3 场景三：快速重路由——多维工件联合一致性要求

快速重路由程序（Fast Reroute）实现 IP 快速重路由功能。入口流水线先按目的前缀查询主下一跳，再读取链路状态寄存器；若主链路标记为故障则切换到备份下一跳，并重写二层地址后转发，实现无控制面实时介入的本地快速绕行。

针对该程序的 P4LTL 时序规范可表述为：

```
//#LTLVariables: a:bv32
//#LTLProperty: [](AP(meta.linkState > 0 && meta.dst == a && !drop)
    ==> AP(fwd(meta.alternativePort)))
//#LTLProperty: [](AP(meta.linkState == 0 && meta.dst == a && !drop)
    ==> AP(fwd(meta.primaryPort)))
//#LTLFairness: [](AP(valid(hdr.ipv4)))
```

第一条性质声明：当链路状态指示故障时，流量应通过备份端口转发。第二条性质声明：正常状态下流量走主端口。自由变量 `a` 抽象了目的前缀。

该场景的复杂性在于：将上述时序规范转化为可执行测试用例需要**四个维度的工件在统一时间线上协调一致**：

**维度一：控制面规则。** 交换机需要预写入主下一跳表项、备份下一跳表项和相关的二层地址重写规则。这些规则的匹配键、动作参数必须与拓扑中的实际端口号和 MAC 地址严格对齐。

**维度二：外部操作动作。** 测试执行过程中需要在特定时间点执行"断开指定链路"（改变 `linkState` 寄存器）和"通知控制器重收敛"等外部操作。这些操作不在 P4LTL 规范的时序算子中显式出现，而是规范成立的环境前提。

**维度三：数据面报文序列。** 测试需要在断链前、断链后和控制器收敛后分别发送流量，并观察转发路径的变化。报文字段必须与控制面规则的匹配键一致，才能命中目标表项。

**维度四：观测预言机。** 每个阶段的预期行为不同——正常时走主路径对应 `fwd(primaryPort)`，故障后走备份路径对应 `fwd(alternativePort)`。预言机必须与场景结构和操作时序对齐。

P4LTL 规范通过 `meta.linkState > 0` 和 `meta.linkState == 0` 的条件分支表达了两种路径选择逻辑，但要在真实环境中触发这两种状态，需要协调控制面配置、外部操作和数据面报文的精确时序。四个维度中任何一个出现错误都会导致测试无效。

该场景集中暴露了**挑战三**的核心矛盾：P4LTL 规范以声明式方式描述了不同状态条件下的转发性质，但将其转化为可执行测试需要多个异质维度的工件在语义上相互一致，而开放式生成几乎不可能在一次输出中同时保证所有维度的正确性，必须通过分阶段生成与确定性校验来逐步收敛。
